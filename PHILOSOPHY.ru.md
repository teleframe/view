## 1. Предыстория: опыт веб-разработки и боль ботов

Как фулстек веб-разработчик, привыкший к чистоте и типобезопасности современного стека (SvelteKit на фронтенде, Bun, Elysia и Hono на бэкенде), я написал множество Telegram-ботов. И каждый раз я натыкался на непреодолимую пропасть между стандартами веба и разработкой ботов.

Стандартные инструменты сообщества (например, `grammY conversations`) — это предельно «голый» низкоуровневый плагин. С ним тяжело работать: императивные шаги и потеря контекста превращают многошаговые формы в спагетти. А когда сообщение динамическое и в нём должно меняться множество параметров, традиционная склейка строк превращалась в кошмар:

```ts
// Традиционный хрупкий подход:
const text =
    `*Заказ #${order.id}*\n\nКлиент: ${user.name}\nСумма: *${order.total}₽*\n` +
    (order.isExpress ? '⚡ _Срочная доставка_\n' : '') +
    `\nТовары:\n${order.items.map((it, i) => `${i + 1}. ${it.title} — ${it.price}₽`).join('\n')}`;
```

Три фундаментальные боли преследовали каждого разработчика:

1. **Капкан экранирования MarkdownV2 и HTML**: в MarkdownV2 нужно помнить о 18 служебных символах (`_`, `*`, `[`, `]`, `(`, `)`, `~`, `` ` ``, `>`, `#`, `+`, `-`, `=`, `|`, `{`, `}`, `.`, `!`). Ошибка в нике (`John (Dev)`) или артикуле (`SKU_123`) роняет бота с `can't parse entities`. Разработчики бегут в HTML-режим, но там их ждет та же ловушка: любой знак `<`, `>` или `&` в пользовательском вводе (`Tom & Jerry`, `a < b`) или незакрытый тег приводят к мгновенному краху.
2. **Хаос управления обновлениями (In-place vs New Message)**: Telegram умеет редактировать сообщения (`editMessageText`), но делать это вручную — сущий ад. Нужно вручную отслеживать `message_id`, ловить ошибки `message is not modified` и разруливать гонки состояний. Из-за отсутствия внятной архитектуры разработчики либо сдаются и спамят чат новыми сообщениями, либо пишут тонны хрупких костылей.
3. **Невозможность масштабирования**: таблицы, списки и динамические виджеты превращают код в нечитаемое месиво конкатенаций и `\n\n`.

## 2. Опыт `tg-widgets` и ресёрч существующих решений

Чтобы облегчить разработку типовых интерфейсов, я создал библиотеку [`tg-widgets`](https://www.npmjs.com/package/tg-widgets) (ныне **deprecated**). Она дала готовые утилиты: пагинацию, псевдографические таблицы и меню. Но это была лишь «заплатка» поверх процедурного хаоса склейки строк.

Тогда я провёл глубокий ресёрч экосистем Python, JavaScript и других языков:

- **Python (`aiogram-dialog`)**: отличная идея GUI-окон на FSM, но вывод текста завязан на шаблонизатор **Jinja2** (`Jinja("<b>{{ name }}</b>")`). Это снова возврат к нетипизированным строкам без проверки пропсов компилятором. А модуль `aiogram.utils.formatting` — это процедурный функциональный builder, на котором мучительно собирать сложные составные экраны.
- **Node.js / TypeScript (`@grammyjs/menu`, `@elumixor/react-telegram`)**: плагины меню решают только кнопки, оставляя текст сырой строкой. Попытки же притащить React тянут за собой тяжелый рантайм React с Virtual DOM и хуками, что совершенно избыточно для серверного вывода.

И тогда пришло главное озарение:

> **Все форматы сообщений в Telegram (HTML `parse_mode`, Telegraph, карточки и виджеты) — это единое абстрактное дерево документов (AST). Ровно такое же, как DOM в веб-разработке.**

## 3. Перенос философии SPA и парадокс JSX

Из опыта со **SvelteKit** родилась идея перенести ментальную модель веб-фреймворков в Telegram:

- **Бэкенд/Сервер SPA** — это код бота (запросы к БД, авторизация, бизнес-логика, FSM-состояния).
- **Фронтенд/View** — это разметка Telegram-сообщения, описанная через типобезопасные компоненты.

### Почему синтаксис React без самого React?

Как разработчик на Svelte, я открыто не люблю React. Его бесконечные перерендеры, ментальная гимнастика с хуками, замыканиями и тяжелый Virtual DOM всегда казались мне странными. React стал стандартом чисто благодаря историческому таймингу после AngularJS (тот же Solid исправил концепции изящнее, но появился позже).

Но для ботов ключевым открытием стало: **JSX $\neq$ React**.
JSX — это не фреймворк, а гениальный синтаксический сахар для описания абстрактных деревьев данных (AST):

- **Никакого рантайма React**: никаких хуков, `useEffect` и тяжелого Virtual DOM. Компоненты — это чистые синхронные функции.
- **Нативная поддержка**: среды (**Bun**, **Node.js**, **Deno**) парсят JSX из коробки без сборщиков (zero-config).
- **100% строгая типизация**: TypeScript проверяет пропсы и структуру дерева прямо в IDE.
- Мы получаем компонентную чистоту веба и **нулевой оверхед** — дерево сериализуется в Telegram HTML за один линейный проход.

## 4. Концептуальный сдвиг: «Каждое сообщение — это страница»

- **Сообщение в боте — это реактивная страница (Page).**
- По умолчанию клики по кнопкам вызывают бесшовный `editMessageText`, обновляя текущий экран на месте.
- Чат остаётся кристально чистым, а пользователь получает мгновенный отклик без перезагрузок.

## 5. До и После: наглядное сравнение

```tsx
// БЫЛО: процедурный ад, ручное экранирование каждого поля, ручная верстка таблиц
const escapeHtml = (s: string) =>
    s.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;');
const renderOrderPageHtml = (order: Order): string => {
    // Вручную вычисляем отступы колонок и рисуем границы псевдографики:
    const rows = order.items
        .map(
            (it) =>
                `│ ${escapeHtml(it.title).padEnd(12)} │ ${String(it.qty).padStart(3)} │ ${String(it.price).padStart(6)}₽ │`,
        )
        .join('\n');
    const table = `<pre><code>┌──────────────┬─────┬──────────┐\n${rows}\n└──────────────┴─────┴──────────┘</code></pre>`;

    // Вручную считаем символы прогресс-бара:
    const filled = Math.round((order.progress / 100) * 10);
    const progress = `<code>[${'█'.repeat(filled)}${'░'.repeat(10 - filled)}] ${order.progress}%</code>`;

    // Склейка с тернарниками (забытый escapeHtml на любом поле роняет бота):
    return (
        `<b>📦 Заказ #${escapeHtml(order.id)}</b>\n\n` +
        `Клиент: ${escapeHtml(order.user.name)}\n\n` +
        table +
        '\n\n' +
        (order.isPriority ? '<b>⚡ Экспресс-доставка</b>\n\n' : '') +
        progress
    );
};

// СТАЛО: чистый, типобезопасный компонент с автоматическим экранированием
const OrderPage = ({ order }: { order: Order }) => (
    <>
        <Paragraph>
            <Bold>📦 Заказ #{order.id}</Bold>
            <Br />
            Клиент: {order.user.name}
        </Paragraph>
        <Table
            data={order.items}
            columns={[
                { header: 'Товар', key: 'title', align: 'left' },
                { header: 'Кол-во', key: 'qty', align: 'center' },
                { header: 'Цена', key: 'price', align: 'right' },
            ]}
            style="rounded"
        />
        <Show when={order.isPriority}>
            <P>
                <Bold>⚡ Экспресс-доставка</Bold>
            </P>
        </Show>
        <ProgressBar value={order.progress} total={100} style="bar" showPercent mono />
    </>
);
```

## 6. Модульная архитектура экосистемы

1. **`@telegram-markup/native` (Релиз v0.1.0 — готов к продакшну)**: автоэкранирование `&`, `<`, `>`, семантические теги `<Paragraph>` и `<P>`, моноширинные `<Table>`, прогресс-бары `<ProgressBar>`, списки `<Ul>`/`<Ol>`, условный рендеринг `<Show>` и обход `<Each>`, поддержка Bot API 9.0 (`<tg-time>`, `<tg-emoji>`, цитаты).
2. **`@telegram-markup/rich-text` (В разработке)**: карточки, карусели и адаптивные блоки.
3. **`@telegram-markup/widget` (В планах)**: интерактивные формы, выбор дат, пагинаторы со стейтом.
4. **`@telegram-markup/telegraph` (В планах)**: публикация лонгридов в Telegraph прямо из JSX.

## 7. Следующий шаг: `@telegram-markup/router` как конечный автомат (FSM)

Вместо хрупких императивных `conversations` разрабатывается **`@telegram-markup/router`** для [grammY](https://grammy.dev).

Фундаментальный принцип архитектуры: **Каждый `Router` управляет жизненным циклом одного интерактивного сообщения**, а каждый **`Route` — это экран (состояние FSM)**, бесшовно обновляющий это сообщение на месте через `editMessageText`.

Для пошаговых сценариев (визарды, редактирование профиля, настройки) роутеры вкладываются друг в друга как изолированные подмашины состояний (Sub-FSM):

```tsx
// Главный роутер, привязанный к интерактивному сообщению:
<Router start="catalog">
    <Route path="catalog" component={CatalogPage} />
    <Route path="profile" component={ProfilePage} />

    {/* Вложенный Sub-FSM роутер для многошагового ввода данных: */}
    <Route path="profile/edit">
        <Router start="set-fio" mode="in-place">
            <Route path="set-fio" component={SetFioStep} />
            <Route path="set-age" component={SetAgeStep} />
            <Route path="confirm" component={ConfirmStep} />
        </Router>
    </Route>
</Router>
```

**Гибкость режимов FSM**:

- **In-place SPA режим (`mode="in-place"`)**: роутер редактирует текущее сообщение на месте, автоматически управляя историей стека для кнопки «Назад».
- **Режим нового сообщения (`mode="new-message"`)**: если сценарий требует открыть новую ветку диалога, роутер отправляет отдельное сообщение как самостоятельный контейнер для нового FSM.

## 8. Преимущества и специфика платформы Telegram

### Преимущества

- 🛡️ **Абсолютная надёжность**: автоэкранирование навсегда исключает падения парсера Telegram.
- 🧩 **Чистота архитектуры**: переиспользуемые UI-компоненты и изолированные экраны.
- ⚡ **Ультрабыстродействие**: линейная трансляция дерева в Bun без накладных расходов.

### Ограничения платформы и опыт тестирования

- **Лимит символов**: не более 4096 символов в сообщении (1024 для медиа-подписей). Это жесткое ограничение Bot API (знакомое нам ещё по `tg-widgets`), требующее постраничной пагинации.
- **Частота редактирования**: обновление не чаще 1 раза в секунду во избежание ошибки `429 Too Many Requests`.
- **Особенности рендеринга таблиц и опыт Android**:
    - На Desktop (macOS, Windows, Linux) и в Telegram Web таблицы `<Table>` в тегах `<pre><code>` отображаются идеально.
    - На Android системный моноширинный шрифт может сбивать сетку колонок.
    - **Ключевой вывод тестов**: это поведение **абсолютно не зависит от «Компактного режима» (Compact Mode)** в Telegram. Мы убрали лишние мобильные костыли из кода: для мобильных экранов рекомендуется использовать лаконичные таблицы (2–3 колонки) или списки `<Ul>`/`<Ol>`.
